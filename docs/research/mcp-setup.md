# Research: MCP setup per Agent and the binary's stable path

Ticket: [#139](https://github.com/stefanhoth/unfocused/issues/139). Findings only, with sources; no decisions.
Researched 2026-11-17 (macOS 27.2.1 host, Claude Code 2.1.308). Anything not backed by a fetched primary source is marked **not verified**.

## 1. How unfocused-mcp is built and linked today (this repo)

- `scripts/build-app.sh` copies the SwiftPM-built `unfocused-mcp` to `<app>/Contents/MacOS/unfocused-mcp` next to the main `Unfocused` executable. Comment in the script: "the cask links it onto PATH".
- Signing, inside out: `unfocused-mcp` first (`--options runtime`, no entitlements), then the bundle (hardened runtime plus `scripts/Unfocused.entitlements`, Apple Events only). Release uses the stable self-signed certificate (`scripts/sign-app.sh`, ADR 0003); local builds without the certificate sign ad hoc (`scripts/build-app.sh`). No notarization (ADR 0003, `README.md`: approve via Privacy & Security, Open Anyway, after each install or update).
- `scripts/check-bundle.sh` verifies `codesign --verify --strict` on app and binary, hardened runtime, no entitlements, and an `initialize` round trip.
- The cask is generated by `scripts/write-cask.sh` and contains `binary "#{appdir}/Unfocused.app/Contents/MacOS/unfocused-mcp"`. The committed `Casks/unfocused.rb` (version 2026.11.02) has **no** `binary` line, because it predates the generator change (commit ea1013c); the line appears with the next release.
- `docs/DECISIONS.md` (2026-11-04): the first `codesign --verify --strict` and Gatekeeper-via-`PATH` result "is pending the first release that ships it" and is to be recorded there. `docs/release-checklist.md` section "Agent access" lists the commands (`spctl --assess --type execute -vv "$(which unfocused-mcp)"` and an `initialize` piped into `unfocused-mcp`). Nothing recorded yet; no binary link exists on this machine (`/opt/homebrew/bin/unfocused-mcp` absent).
- Current setup instructions (`README.md`, `Sources/Unfocused/AgentAccessSection.swift`): `claude mcp add unfocused -- unfocused-mcp`; for other apps a JSON `mcpServers` entry with `"command": "unfocused-mcp"`; fallback absolute path `/Applications/Unfocused.app/Contents/MacOS/unfocused-mcp`.
- The server takes no arguments and needs no environment (`README.md`, `docs/local-development.md`). It logs to stderr and `~/Library/Logs/unfocused/unfocused-mcp.log`; stdout is protocol only.
- `docs/adr/0007-read-only-agent-access-through-mcp.md` is referenced by the README, scripts and docs but is not present in `docs/adr/` on this branch or on `origin/main` (only 0001 to 0006).

## 2. Per-Agent registration of a local stdio server

### Claude Code
Source: https://code.claude.com/docs/en/mcp (first ~100k of 156k characters read).
- CLI: `claude mcp add [options] <name> -- <command> [args...]`; "Everything after `--` is passed to the server untouched."
- Scopes and storage: local (default, current project only) and user (all projects) are stored in `~/.claude.json`; project scope is `.mcp.json` in the project root (shared via version control). Precedence local > project > user > plugin-provided > claude.ai connectors; the whole entry from one source is used, fields are not merged.
- `claude mcp add-json <name> '<json>'` accepts a stdio block such as `{"command":"npx","args":[...]}`. For `mcpServers` JSON written for other clients (e.g. Claude Desktop), pass the inner server object, not the wrapper.
- `.mcp.json` stdio entries use `command`, `args`, `env` under `mcpServers`. `${VAR}` and `${VAR:-default}` expand in `command`, `args`, `env`, `url`, `headers`.
- Project-scoped servers prompt for approval in interactive sessions; reset with `claude mcp reset-project-choices`.
- Plugins can ship MCP servers (`.mcp.json` at plugin root or `mcpServers` in `plugin.json`); `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` resolve in `command`/`args`/`env`. Tool names become `mcp__plugin_<plugin>_<server>__<tool>`.
- Whether `command` is resolved through `PATH`: the page, as read, does not say. A one-click or deeplink install: not found in the part read. Not verified for the unread remainder.

### Claude Desktop
Sources: https://modelcontextprotocol.io/docs/develop/connect-local-servers ; https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop ; https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md
- Manual config: Settings, Developer, Edit Config opens `~/Library/Application Support/Claude/claude_desktop_config.json`. Format `{"mcpServers": {"name": {"command": ..., "args": [...]}}}`. "completely quit Claude Desktop and restart it" to load changes.
- Troubleshooting guidance: file paths in the config "are valid and that they are absolute and not relative". MCP logs: `~/Library/Logs/Claude/mcp.log` and `mcp-server-SERVERNAME.log` (stderr of the server).
- One-click route: Desktop Extensions (`.mcpb`), installed via Settings, Desktop app, Extensions, Advanced settings, Extension Developer, "Install Extension…", or from the directory. Anthropic's article presents this as the way to avoid "manually configuring JSON files". That article does not mention `claude_desktop_config.json`.
- MCPB manifest (current version 0.3): `server.type` is `node`, `python`, `binary` or `uv`; `binary` is "Pre-compiled executable with all dependencies included", "Platform-specific binaries supported"; `entry_point` is required for binary; `mcp_config` has `command`/`args`/`env` with `${__dirname}` for the extension directory and `platform_overrides` (e.g. `darwin`). The page does not state outright that a macOS prebuilt binary is supported, only lists `darwin` in an example. How Claude Desktop treats code signing or quarantine for a bundled binary: **not verified**.
- Whether Claude Desktop (a GUI app) finds a bare command via `PATH` the way Terminal does: **not verified** in any fetched source. The MCP guide only demonstrates `npx` and absolute args paths.

### Cursor
Sources: https://cursor.com/docs/context/mcp ; https://cursor.com/docs/context/mcp/install-links
- Config files: project `.cursor/mcp.json`, global `~/.cursor/mcp.json`.
- Stdio fields: `type` ("stdio"), `command` ("must be on your system path or given as a full path"), `args`, `env`, `envFile`. Interpolation in `command`, `args`, `env`, `url`, `headers`: `${env:NAME}`, `${userHome}`, `${workspaceFolder}`, `${workspaceFolderBasename}`, `${pathSeparator}`.
- Deeplink: `cursor://anysphere.cursor-deeplink/mcp/install?name=$NAME&config=$BASE64_ENCODED_CONFIG`, where config is the server's JSON (without the outer name key) passed through `JSON.stringify` then base64. A `cursor.com` web link variant was not confirmed by the fetched page.

## 3. Does a stable path survive updates? (Homebrew)

Sources: https://docs.brew.sh/Cask-Cookbook ; https://docs.brew.sh/Manpage
- `binary "<path>"` links the source "into the `$(brew --prefix)/bin` directory on installation" (example symlink `$(brew --prefix)/bin/operadriver`). `appdir` paths are allowed in the source: `binary "#{appdir}/Atom.app/Contents/Resources/app/apm/bin/apm"`. `target:` renames the link.
- `brew --prefix` default on Apple Silicon is `/opt/homebrew` (Manpage); Intel `/usr/local`.
- Cookbook says nothing specific about `binary` on upgrade or uninstall. The behaviour of the link across `brew upgrade --cask` (relinked or left dangling when the app is replaced) is **not verified** from docs; it could be tested locally with a test cask.
- The cookbook does not define what `appdir` resolves to, and a non-default `--appdir` is not covered in the fetched text. The repo's README fallback assumes `/Applications`.
- A path inside the app, `/Applications/Unfocused.app/Contents/MacOS/unfocused-mcp`, is the same file the link points at; it exists only while the app is installed there.

## 4. Gatekeeper and codesign on the cask-linked binary

- Apple, "Resolving Gatekeeper Problems Caused by Unnotarized Software" (https://developer.apple.com/forums/thread/706442; Apple DTS-authored): "If you launch a quarantined app, the system invokes Gatekeeper." The system may run Gatekeeper at other times; "The exact circumstances under which it runs Gatekeeper is not documented and changes over time." Quarantine is the `com.apple.quarantine` xattr set by user-level download apps; "Unix-y networking tools, like `curl` and `scp`, don't quarantine the files they download. Unix-y unarchiving tools, like `tar` and `unzip`, don't propagate quarantine." The page does not address Homebrew, Terminal-launched tools, or tools nested in an approved app.
- Apple DTS in https://developer.apple.com/forums/thread/757647: a signed and notarized single-file command-line tool with the quarantine xattr was rejected by Gatekeeper (`spctl -a -vvv` rejected, `-t install` accepted); removing the xattr let it run. DTS asked whether it was run from Terminal or double-clicked in Finder and pointed to the "Tool Blocked by Gatekeeper" section; the thread shows no resolution. Not conclusive for Terminal launches.
- Apple Support, "Safely open apps on your Mac" (https://support.apple.com/en-us/102445): for an unnotarized app, after a blocked launch attempt, Privacy & Security, "Open Anyway", then confirm; the app "is now saved as an exception". The page says nothing about helper executables inside the bundle or about tools started from other processes.
- Whether the approval given to `Unfocused.app` also covers `Contents/MacOS/unfocused-mcp` when started via the `PATH` link by an Agent: **not answered by any primary source found**. This is the check still pending in `docs/DECISIONS.md`; it can only be answered on a real installed release.
- Homebrew policy (https://brew.sh/2025/11/12/homebrew-5.0.0/): `--no-quarantine` and `--quarantine` deprecated ("Homebrew does not wish to easily provide circumvention to macOS security features"); "Casks without codesigning are deprecated"; "We will disable all Homebrew/homebrew-cask casks that fail Gatekeeper checks in September 2026." The page does not extend this to third-party taps. Issue https://github.com/Homebrew/brew/issues/20755 (closed 2025-11-05) names 2026-09-01 and shows maintainers treating manual quarantine removal in tap scripts as equivalent to the flag; a tap-level audit warning was proposed and agreed. https://docs.brew.sh/Acceptable-Casks (core casks): "must not require System Integrity Protection or Gatekeeper to be disabled or bypassed." Removal versions of the flags beyond deprecation come from third-party reports only and were not confirmed against Homebrew docs.
- Whether Homebrew sets the quarantine xattr on a downloaded cask app: implied by the flag's purpose, not stated in the fetched pages.
- The repo's own signing facts: binary and bundle are signed with the same self-signed certificate, hardened runtime on both, binary without entitlements, none notarized (section 1). Apple's notarization docs page (https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) could not be read through the fetch tool, so notarization requirements for nested executables are not quoted here.
